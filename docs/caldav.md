# 日历订阅

让同学的手机日历自动显示课表，改课后自动同步。

先说清楚一件事：**CalDAV 和 ICS 订阅是两回事**，经常被混着叫，但适用场景差别很大。

| | CalDAV | ICS 订阅 |
|---|---|---|
| 本质 | 一套日历协议，系统日历原生支持 | 一个静态 `.ics` 文件挂在 HTTPS 上 |
| **系统自带日历支持度** | **几乎全平台原生支持**：iOS、macOS、Android、鸿蒙、Windows | iOS、macOS、Outlook 可以；**安卓和鸿蒙自带日历大多不支持** |
| 需要服务器 | 需要一台常驻服务器 | 不需要 |
| 需要账号密码 | 需要 | 不需要 |
| 更新及时性 | 通常更快 | 由各平台自己决定，几小时到一天 |
| 维护成本 | 要管服务、备份、密码 | 零 |

**怎么选：**

- **班里有安卓 / 鸿蒙用户（也就是绝大多数班级），推荐用 CalDAV。** 它是唯一能让全班同学都用系统自带日历、不用额外装 App 的方案。安全问题用一个**只读账号**解决，见下面第一节。
- **只是想零成本先跑起来、或者手上没有服务器**，用 ICS 订阅。苹果用户体验一样好，安卓同学需要装一个第三方日历 App。

两个可以同时开。框架开启 CalDAV 后，网页上会把 CalDAV 放在前面，ICS 收进折叠区作为备选。

---

## 一、CalDAV（推荐给有服务器的班级）

### 为什么推荐它

**几乎所有系统自带日历都原生支持 CalDAV**：iOS、macOS、Android、鸿蒙、Windows 都能直接在「添加账户」里配好，同学不用额外装任何 App。

这一点是 ICS 订阅做不到的。安卓和鸿蒙的自带日历大多不支持网址订阅，走 ICS 的话这部分同学只能去装第三方日历，实际落地时会掉一大半人。

顺带还有两个好处：更新更及时；日历名称、颜色这些能由服务端统一控制。

### 关键：给同学的账号必须是只读的

这是整个方案能不能安心用的前提。

CalDAV 本身是可读写协议。给全班共用的那个账号，**必须在服务端把写入权限关掉**，只保留读。否则任何一个同学在自己手机上误删一节课，或者手滑改了时间，都会同步回服务器，全班跟着一起错。

Radicale 的做法是在 `rights` 配置文件里给这个用户只配 `permissions: r`：

```ini
[readonly-students]
user = student
collection = classadmin/schedule
permissions = r
```

Baïkal 则是在后台给日历单独建一个只读共享账号。

具体配法看你用的服务的文档，但**这一步不能省**。配完自己拿手机试一次：删掉一个事件，看服务端有没有跟着变。

### 另一个注意点：密码会出现在网页源码里

网页是公开的，写在配置里的账号密码，任何人查看源代码都能看到。

所以：

- 这个账号只能是**只读、专用、可随时作废**的，反正它读到的内容本来就是公开课表，泄露了也没有额外损失
- **不要复用**任何其他地方的密码
- 毕业了就把账号删掉
- 不想印在页面上的话，`pass` 留空即可，网页会显示「请向课代表索取」

框架在校验阶段会对这件事发出提示。

### 怎么开

先自己搭一个 CalDAV 服务，常见的两个：

- [Radicale](https://radicale.org/) — Python 写的，轻量，配置简单
- [Baïkal](https://sabre.io/baikal/) — PHP 写的，有网页管理后台

然后在 `config.json` 里：

```json
"calendar": {
  "caldav": {
    "enabled": true,
    "server": "caldav.example.com",
    "user": "readonly-student",
    "pass": "",
    "displayName": "课表"
  }
}
```

- `server` 只填域名，前面不要加 `https://`，后面也不要加路径。苹果日历会自己做服务发现。
- `pass` 留空的话，网页上会显示「请向课代表索取」，而不是把密码印出来。**推荐这么做。**

开启后，网页的「订阅」标签页会把 CalDAV 配置指引放在前面，ICS 订阅收进折叠区。

### 把 ICS 灌进 CalDAV

生成的 `.ics` 可以直接推进 CalDAV 服务器。以 Radicale 为例：

```bash
curl -u user:pass \
     -X PUT \
     -H "Content-Type: text/calendar; charset=utf-8" \
     --data-binary @site/dist/calendar.ics \
     https://caldav.example.com/user/calendar-id/
```

具体路径和鉴权方式看你用的服务的文档。可以把这条命令挂在 `npm run build` 后面做成一步。

## 二、ICS 订阅（零成本方案）

### 怎么用

`npm run build` 会生成 `site/dist/calendar.ics`，传到你的静态托管上，订阅地址就是：

```
https://你的域名/calendar.ics
```

网页上的「订阅」标签页里已经内置了各平台的操作步骤和一键复制，直接让同学看那一页就行。

### 服务器要注意的两点

1. **Content-Type 必须是 `text/calendar`。** 配错了 iOS 添加订阅会直接失败。nginx 配置见 [`deploy-web.md`](deploy-web.md)。
2. **必须 HTTPS。** iOS 对 http 的订阅源支持很差。

### 刷新频率的真相

这是最容易被投诉的地方，提前跟同学说清楚：

- **订阅日历不是实时同步的。** 各平台按自己的节奏拉取。
- **Google 日历最长可能到 24 小时**，这是 Google 自己的策略，`X-PUBLISHED-TTL` 和 `REFRESH-INTERVAL` 只是建议，它不一定听。
- **苹果日历**可以在「日历 - 显示简介 - 自动刷新」里调成每小时，也可以在日历列表页下拉手动刷新。
- **急着看变化，直接打开课表网页。** 网页是实时的。

### 生成细节

生成器做了这些事，一般不用管，但出问题时有用：

- **时间统一换算成 UTC 输出**，换算时按 `config.json` 里的 `calendar.timezone` 用系统时区库取真实偏移，所以换到有夏令时的时区也不会错。
- **UID 由内容派生。** 同一条课内容不变，UID 就不变；内容改了，日历会正确识别成「同一事件被修改」而不是新增一条。这是重复订阅不会产生重复事件的原因。
- **`key` 必须唯一。** 两个日期块用了同一个 `key`,UID 会撞车，日历里就会出现事件丢失或错乱。
- **跨零点的课**(比如 22:00 到 01:00)会自动把结束日期顺延一天。
- **全天事件**的 `DTEND` 按 iCalendar 规范自动加一天（规范里全天事件的结束日期是排他的）。
- **课前提醒**由 `calendar.alarmMinutes` 控制，默认 30 分钟。给某条事件加 `"noAlarm": true` 可以单独关掉。

## 三、常见问题

| 现象 | 原因 |
|---|---|
| iOS 添加订阅提示失败 | 服务器 Content-Type 不是 `text/calendar`，或者不是 HTTPS |
| 事件时间整体差 8 小时 | `config.json` 里 `calendar.timezone` 填错了 |
| 日历里出现重复事件 | `DAYS` 里有两个日期块用了同一个 `key` |
| 改了课表，日历没动静 | 正常。见上面「刷新频率的真相」，先手动刷新试试 |
| 取消订阅后事件还在 | 有些平台会把订阅事件复制进本地日历。在日历列表里删掉整个订阅日历 |
| 安卓 / 鸿蒙自带日历找不到订阅入口 | 自带日历大多不支持 ICS 网址订阅，但**支持 CalDAV**。改用 CalDAV 方案即可，不用装第三方 App |
